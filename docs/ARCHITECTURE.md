# Architecture

## Database layer (SQLite, via DB Browser for SQLite)

- One central General Ledger (`journal_entry` + `journal_entry_line`) as the
  single source of truth for all financial facts.
- Sub-ledger tables (`customer`, `sales_order`, `ar_invoice`,
  `cash_receipt`, `vendor`, `purchase_order`, `ap_invoice`,
  `vendor_payment`) reference `journal_entry` via an optional
  `journal_entry_id` foreign key.
- Double-entry bookkeeping is enforced at database level via a CHECK
  constraint on `journal_entry_line`: every line must have exactly one of
  debit/credit greater than 0, never both or neither.
- Every account (`chart_of_accounts`) has a `normal_balance` (Debit/Credit)
  that determines how that account behaves in reporting.
- Composite primary key (`fiscal_year` + `fiscal_period`) on
  `fiscal_calendar` to tie postings to periods. `journal_entry`,
  `close_checklist`, and `budget_line` all reference this composite key.

## Process structure — all three cycles complete

- **O2C (Order-to-Cash)**:
  `customer` → `product` → `sales_order` → `sales_order_line` →
  `ar_invoice` → `cash_receipt`, each linked to the GL. Tested end-to-end:
  order → invoice → payment, with correct postings at every step.
- **P2P (Procure-to-Pay)**, mirror image of O2C:
  `vendor` → `purchase_order` → `purchase_order_line` → `ap_invoice` →
  `vendor_payment`. Tested end-to-end with the same rigor as O2C.
- **R2R (Record-to-Report)**:
  `close_checklist` (period-close task tracking, composite FK to
  `fiscal_calendar`) and `budget_line` (per-account monthly budgets,
  compared against actuals via a correlated subquery).

## Reporting layer — six views, all reading exclusively from the GL

- `v_trial_balance` — per-account balance, normalised for Debit/Credit
  accounts via `CASE WHEN normal_balance = ...`
- `v_ar_aging` / `v_ap_aging` — open invoices bucketed by days past due,
  using `julianday()` date arithmetic and a multi-branch `CASE WHEN`
- `v_income_statement` — revenue, expenses, and net income in a single row
- `v_close_status` — percentage of close-checklist tasks completed, per
  period
- `v_budget_vs_actual` — budgeted vs actual amount per account/period,
  using a correlated subquery against `journal_entry_line`

All views read only from `journal_entry_line` and the sub-ledger tables —
never from anywhere else — so reporting always stays consistent with
whatever is actually posted in the GL.

## Data generation layer (Python) — feature-complete

`scripts/generate_data.py` rebuilds the entire schema and seeds it with a
realistic single-year dataset programmatically — the same 17 tables, the
same constraints, but created via `CREATE TABLE` statements executed from
Python, and populated using controlled randomness rather than fixed
values. `random.seed(42)` is set once at the top of the script, so every
run produces byte-for-byte the same "random" dataset — reproducible, not
arbitrary.

**Master data**, generated by combining randomised name-parts rather than
hardcoding each record: 20 customers, 15 products (with cost-based
pricing — sale price is always derived from cost plus a randomised
markup, so no product is ever sold at a loss), and 12 vendors.

**Transaction volume**: 150 sales orders and 100 purchase orders, each
assigned a random customer/vendor, product, quantity, and order date
spread across the full year via a custom `random_date_2025()` function.
Product prices and costs are looked up live from the `product` table at
generation time rather than duplicated or guessed.

**Realistic invoicing and payment ratios**, deliberately short of 100% on
both steps so the resulting dataset has genuinely open items for AR/AP
ageing to report on:
- ~83% of sales orders are invoiced; of those, ~74% are paid (leaving 32
  open AR invoices)
- ~82% of purchase orders are invoiced; of those, ~73% are paid (leaving
  22 open AP invoices)

Each invoice/receipt/payment still goes through the same fully automated,
GL-correct posting pattern first proven by hand in SQL and then in a
small fixed-data Python loop — only the source of the values (fixed vs.
randomly selected/looked-up) has changed.

**Both previously known gaps have been resolved:**
- An opening capital entry (`Dr Cash / Cr Common Stock`, €1,000) is
  posted before any other transaction, so Cash reflects real funding
  instead of drifting negative purely because expenses were recorded
  before any capital was.
- Every AR invoice now also posts a matching `Dr COGS / Cr Inventory`
  line (currently a simplified 50%-of-sale-price cost assumption), so
  Inventory correctly decreases on sale instead of only ever increasing
  via P2P purchases.

With these fixes, the full dataset (232+ transactions across both cycles)
still balances exactly — `SUM(debit_amount) - SUM(credit_amount) = 0`
across the entire `journal_entry_line` table — regardless of the volume
or randomness involved.

## Why this design?

The core guarantee of this system is that the books **always** balance,
regardless of whatever application ends up running on top of it. By
enforcing double-entry at the database level (not in application code), no
future bug, script, or ad-hoc SQL statement can ever write an unbalanced
posting — the database simply refuses it. This was verified directly: a
missing pair of `journal_entry_line` rows (from an early manual mistake)
was caught by the trial balance view itself, before it caused any further
harm — see `LESSONS_LEARNED.md`. It was verified again at scale: after
generating 232+ randomised transactions, the same balance check still
returns exactly zero.

## Version control

The project is tracked in Git and hosted on GitHub
(`github.com/NikiDigitals/general-ledger-engine`), including the SQLite
database file itself, all documentation, and the ERD — so the full state
of the project at any point is reproducible from the repository alone.

## Backend API layer (Node/Express) — in progress

`backend/server.js` is a running Express server that reads from the same
`erp_demo.db` used by the Python generator and the SQL views — the same
database file, three different consumers (SQL client, Python script,
HTTP server), never a separate copy of the data.

**Live so far:** `GET /api/accounts`, returning the full chart of
accounts as JSON. Uses `better-sqlite3` — a synchronous SQLite driver for
Node, chosen deliberately over the more common asynchronous
`sqlite3` package because synchronous calls read like the Python version
already built (`db.prepare(...).all()` versus `cursor.execute(...)`;
`cursor.fetchall()`), which keeps the two languages easy to compare while
learning.

**Two usage modes decided, not yet built:** a single application and
schema will serve both a demo database (`erp_demo.db`, pre-seeded) and a
personal-use database (to be created, starting empty except for the
chart of accounts), selected via a `DB_PATH` environment variable rather
than separate application logic — see `DECISIONS.md`.

**Accounting-standard rule for all future CRUD routes:** wherever a
technical shortcut and an accounting standard conflict, the accounting
standard wins. Concretely, this means `chart_of_accounts` will support
soft-delete (`is_active = 0`) for any account already used in a posting,
and only a true hard delete for an account that has never been posted to
— never a delete that could orphan historical `journal_entry_line` rows.

## Future extensions

Ideas surfaced during the build that are deliberately out of scope for
now, but fit the current architecture without requiring a redesign — kept
here so they aren't lost, and so the reasoning for *why* they'd be easy is
recorded alongside the idea itself.

**Manual journal entry screen (frontend)**
The opening capital entry, and any future one-off correction, is
hardcoded in the Python generator today — appropriate for a data
generator, but not for a real application. The eventual frontend should
include a generic "Manual Journal Entry" screen: a date, a description,
and a set of lines (account + debit/credit amount), with the same
balance CHECK enforced server-side. This makes the generator's opening
entry just one example of what any user could type in, rather than a
special case baked into setup code.

**Discounts**
Two distinct mechanisms, not one: a *line-level* discount (applied before
invoicing, e.g. `discount_percent` on `sales_order_line`, needs no new
account) versus a *post-invoice* credit to a customer, which would post
through a new `Sales Discounts` account (Debit-normal, reducing revenue)
via `Dr Sales Discounts / Cr Accounts Receivable`.

**Reversals**
Never delete or edit an existing posting. A correction is always a new,
opposite journal entry (what was Dr becomes Cr and vice versa). No schema
change is strictly required, but a `reverses_journal_entry_id` column on
`journal_entry` would preserve the audit trail by making the
original/correction relationship explicit and queryable.

**Write-offs**
Same posting pattern as any other transaction —
`Dr Bad Debt Expense / Cr Accounts Receivable` — paired with extending the
`ar_invoice.status` CHECK constraint to include a `'Written Off'` value.

**More accurate COGS costing**
The current COGS posting assumes a flat 50% of sale price per invoice.
Since each `sales_order_line` already references a specific `product_id`,
a more accurate version would look up that product's actual `unit_cost`
and multiply by the line's `quantity`, the same way price is already
looked up live rather than guessed.

**Multi-currency**
Not needed while everything is in a single currency (only the display
symbol would change, e.g. € to £, which is cosmetic and touches no
table). Real multi-currency (different customers/vendors invoiced in
different currencies) would require a deliberate addition: a
`currency_code` column plus an exchange-rate table, converted to a base
currency before GL posting.

**Accounting-style negative number formatting**
Displaying negative balances as `(150)` instead of `-150` is a display-only
concern, not a schema or posting change — handled with a `CASE WHEN` in a
view or reporting query (or equivalent formatting logic in the frontend),
never in how the number is stored.

**The common thread**: none of the above require changing the
architecture itself. They are new rows in tables that already exist
(`journal_entry`, `journal_entry_line`), occasionally with one new column
or an extended CHECK list — which is the practical payoff of having a
single, centrally-enforced GL from the start.
